Do WinForms para a web,
sem perder uma regra

Análise do sistema de portaria em C# + SQLite, arquitetura Node proposta e plano de corte em sete fases. Nenhuma linha de código de aplicação foi escrita — o que falta são doze decisões suas.

4 fluxos · 7.600 linhas de C# 24.791 acessos · 28 MB 38 regras mapeadas 3 decisões bloqueiam o início

1 · O que o sistema faz hoje

Quatro fluxos, operados por 14 porteiros em três turnos. A tela principal Frm_Veiculo.cs tem 1.375 linhas e concentra quase tudo; fechá-la encerra o programa.

Agendamento não existe

O módulo foi removido do código em 27/08/2026 e a tabela ficou órfã com 2 linhas. A estrutura pedida no briefing lista “Agendamentos” dentro da Portaria — não há nada para migrar. Se voltar, volta como requisito novo. Também não existem cadastros de pessoas, veículos, empresas ou fornecedores: “prestador” e “agregado” são dois campos de texto na linha do acesso.

4 · As regras que não podem mudar

5 · Arquitetura proposta

Monorepo com npm workspaces. O pacote shared é o coração da fidelidade: as regras de Mascaras.cs viram funções puras usadas pelo backend e pelo frontend, testadas uma vez só.

IMPAKTO-PORTARIA/
├── apps/
│   ├── api/        Node 22 · TypeScript · Fastify 5 · Zod · Prisma
│   │   └── src/modules/
│   │       ├── auth/  usuarios/  auditoria/
│   │       └── portaria/   ← fase 1
│   │           └── acessos/ busca/ pessoas/ veiculos/
│   │              mercadorias/ relatorios/
│   │       (compras/ rh/ ti/ financeiro/ — pastas futuras)
│   └── web/        React 19 · Vite · Tailwind v4 · TanStack Query
└── packages/
    └── shared/     placa · documento · CPF · senha PBKDF2

Cada submódulo tem sempre os mesmos quatro arquivos — rotas, serviço, repositório e schema. Regra de negócio nunca mora na rota. Adicionar Compras é criar uma pasta e uma linha em app.ts; nada do que existe é tocado.

Permissões sem inventar comportamento

O briefing pede Usuário → Perfil → Permissões → Módulo; o C# tem só dois níveis. Os 14 usuários migram para ADMINISTRADOR (2) e PORTARIA (12) — ninguém ganha nem perde acesso. Os perfis GESTOR e CONSULTA nascem na estrutura, sem usuários, para a granularidade existir sem mudar nada hoje. E a proteção continua em duas camadas: o menu esconde a rota e o backend revalida. Esconder botão não é autorização.

As conferências que barram o deploy

Não são checklist manual — são asserts no script. Se qualquer uma não bater, a migração falha.

ConferênciaEsperado

Recontagem obrigatória

Estes números são de hoje e o desktop segue em produção a ~2.900 entradas por mês. Rode as contagens de novo imediatamente antes da migração final e use os valores frescos como gate — não estes.

Regras invioláveis

O script de migração só lê — nunca apaga nem altera o banco original, e roda sempre sobre uma cópia com md5 conferido. É idempotente, via legado_id. E desktop e web nunca escrevem ao mesmo tempo: SQLite em arquivo não tolera dois donos.

Risco a tratar antes de tudo

O banco de produção vive em bin/Debug/. Um Clean do Visual Studio apaga a cópia de trabalho, e o que foi cadastrado desde o último refresh não volta. Tirar o banco da pasta de build e ligar backup diário é independente da migração — e é para ontem.

8 · Doze decisões que são suas

Nenhuma dessas lacunas foi preenchida por suposição. As três primeiras precisam de resposta antes da fase 0; as demais podem esperar até a fase que as consome.

DV1
PostgreSQL ou SQL Server?

Existe licença de SQL Server disponível? O Prisma suporta os dois — trocar agora é barato, depois da fase 4 é caro.

Proposta: PostgreSQL 16.
DV2
Onde o sistema vai rodar?

Servidor interno já existe ou precisa ser provisionado? Só rede interna, ou também pela internet? Decide HTTPS, certificado, VPN e CORS.

DV4
Como gerar os PDFs?

O QuestPDF não existe em Node. Puppeteer renderiza HTML/CSS mas pede Chromium no servidor; pdfmake é leve e mais trabalhoso em paisagem.

Proposta: Puppeteer — os relatórios precisam bater visualmente com os do desktop na homologação.
DV3
Cadastro de pessoas já na fase 2?

A busca continua sendo “última visita”, como o porteiro está acostumado, ou vira cadastro consultável?

Proposta: manter o hábito na fase 2, liberar o cadastro na fase 3. O modelo suporta as duas.
DV5
Por quanto tempo guardar os dados?

A base tem CPF, RG, nome e celular de ~12.800 pessoas. A retenção precisa de definição do jurídico (LGPD).

DV6
Quem revisa os tipos de veículo?

Consolidar ¾, 3/4 e 3/4. num tipo só exige alguém da portaria aprovando o de-para antes da fase 4.

DV7
Agendamento volta?

Removido do desktop, tabela órfã. Se voltar, volta como requisito novo com modelagem própria — não como migração.

DV8
Quanto dura a sessão?

Turno de 8h sem re-login, ou expiração curta com refresh? Na web não existe “fechar o programa” para auditar.

Proposta: token de 15 min + refresh de 12h em cookie httpOnly.
DV9
Manter o beep da placa?

O desktop apita ao recusar caractere inválido. No navegador isso exige AudioContext e pode incomodar no balcão.

DV10
Continuam sendo 5 ajudantes?

Zero registros usam do 2º ao 5º — o limite nunca foi exercitado.

Proposta: manter 5 como validação configurável; a tabela não impõe limite.
DV11
Vai existir mais de uma guarita?

Prever a coluna de portaria nas tabelas de movimento custa quase nada agora e caro depois.

DV12
Como é a rede da guarita?

Wi-Fi ou cabo? Tablet no horizonte? A escolha por SPA já tolera rede instável, mas o WebSocket precisa de fallback por polling.
